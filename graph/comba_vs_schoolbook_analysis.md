## 観察される現象

1. **16bit**: Combaの方が速い（-2.7サイクル）
2. **32bit以降**: Schoolbookの方が速い（+0.18～+0.49サイクル）
3. **bit幅が大きくなるほど**: Combaの不利が拡大する傾向

## Comba乗算のレイテンシが大きい理由

### 1. 複雑なビット抽出処理

**Comba乗算**では、各対角の計算で `get_bits_as_chunk()` を呼び出します：

```cpp
const chunk_t aj = get_bits_as_chunk(a, nwords, a_bitpos);
const chunk_t bj = get_bits_as_chunk(b, nwords, b_bitpos);
```

この関数は：
- 複数のDigitからビットを抽出
- ビット位置の計算が必要
- 条件分岐が含まれる
- **追加のレイテンシオーバーヘッド**が発生

**Schoolbook乗算**では：
- 単純な `A.range()` アクセス
- 直接的なビット範囲アクセス
- オーバーヘッドが小さい

### 2. ChunkPackerによるパッキング処理

**Comba乗算**では、結果を `ChunkPacker::push()` でパックします：

```cpp
pack.push(out);
```

この処理は：
- chunk_t（64bit）をDigit配列に分割
- ビットシフトとマスク操作が必要
- 複数のループ反復が必要な場合がある
- **追加のレイテンシ**が発生

**Schoolbook乗算**では：
- 単純な `ACC += term` の累積
- 最後に一度だけ `unpack()` を実行
- パッキングのオーバーヘッドが小さい

### 3. 二重ループの構造の違い

**Comba乗算**:
```cpp
for (unsigned t = 0; t < N_OUT; ++t) {  // 外側ループ
    for (unsigned j = j_start; j <= j_end; ++j) {  // 内側ループ
        // ビット抽出 + 乗算 + 加算
    }
    pack.push(out);  // 各対角ごとにパッキング
}
```

- 外側ループの各反復で `pack.push()` を実行
- パイプライン化されていても、パッキング処理がボトルネック

**Schoolbook乗算**:
```cpp
for (unsigned i = 0; i < nblocks; ++i) {
    for (unsigned j = 0; j < nblocks; ++j) {  // パイプライン化
        // 直接アクセス + 乗算 + 加算
    }
}
// 最後に一度だけ unpack()
```

- 内側ループが完全にパイプライン化
- パッキング処理が最後に一度だけ

### 4. チャンクサイズの違い

**Comba乗算**: CHUNK_BITS = 64（固定）
- 64bitのチャンクを処理
- ビット抽出が複雑になる

**Schoolbook乗算**: BLOCK_BITS = 16（固定）
- 16bitのブロックを処理
- より細かい粒度で処理
- パイプライン化が効率的

### 5. メモリアクセスのパターン

**Comba乗算**:
- 対角ごとに異なるビット位置からアクセス
- メモリアクセスのパターンが不規則
- キャッシュ効率が悪い可能性

**Schoolbook乗算**:
- 順次的なメモリアクセス
- 規則的なアクセスパターン
- キャッシュ効率が良い

### 6. 条件分岐の影響

**Comba乗算**では：
- `get_bits_as_chunk()` 内に条件分岐
- `j_start` と `j_end` の計算が動的
- 条件分岐によるパイプラインストールの可能性

**Schoolbook乗算**では：
- 単純な範囲チェック
- 条件分岐が少ない
- パイプラインが効率的に動作

## 定量的分析

### レイテンシの内訳（推定）

**Comba乗算（64bitの場合）**:
- ビット抽出: ~0.2サイクル/対角
- 乗算: ~0.1サイクル/対角
- 加算: ~0.1サイクル/対角
- パッキング: ~0.3サイクル/対角
- **合計**: ~0.7サイクル/対角 × 約2対角 = ~1.4サイクル

**Schoolbook乗算（64bitの場合）**:
- メモリアクセス: ~0.05サイクル/ブロック
- 乗算: ~0.1サイクル/ブロック
- 加算: ~0.05サイクル/ブロック
- **合計**: ~0.2サイクル/ブロック × 約4ブロック = ~0.8サイクル

### オーバーヘッドの比較

| 処理 | Comba | Schoolbook | 差 |
|------|-------|------------|-----|
| ビット抽出 | 必要 | 不要 | +0.2サイクル |
| パッキング | 各対角 | 最後のみ | +0.3サイクル |
| メモリアクセス | 不規則 | 規則的 | +0.1サイクル |
| **合計オーバーヘッド** | **+0.6サイクル** | **0** | **+0.6サイクル** |

## なぜ16bitではCombaが速いのか？

16bitの場合：
- 対角数が少ない（N_OUT ≈ 1-2）
- パッキングのオーバーヘッドが小さい
- ビット抽出の複雑さが小さい
- **Combaのアルゴリズム効率が優位**

32bit以降：
- 対角数が増加
- パッキングのオーバーヘッドが累積
- ビット抽出の複雑さが増加
- **Schoolbookのシンプルさが優位**

## 結論

Comba乗算のレイテンシが大きい主な理由：

1. **ビット抽出処理のオーバーヘッド**: `get_bits_as_chunk()` の複雑さ
2. **パッキング処理の頻度**: 各対角ごとに `pack.push()` を実行
3. **メモリアクセスの非効率性**: 不規則なアクセスパターン
4. **条件分岐の影響**: 動的な範囲計算によるパイプラインストール

**最適化の方向性**:
- ビット抽出処理の最適化
- パッキング処理のバッチ化
- メモリアクセスパターンの改善
- 条件分岐の削減

ただし、Comba乗算は**メモリ使用量が少ない**という利点があり、リソース制約がある場合には有効な選択肢となる。
