HLS 合成レポート — Montgomery Multiplication

モンゴメリ乗算器の自動検出・変換パイプライン

ビット単位のリファレンス実装から出発し、語単位CIOSへの再実装、 montgomery_auto_rewriterによる自動検出・置換、 呼び出し箇所統合によるリソース削減、窓法による高速化、 コア差し替えによる極小化までを検証し、速度重視・バランス・ リソース最小の3オプションを確立した記録(実際のRSA-512 modExp演算)。

1

検出機構

montgomery_auto_rewriter(Clang LibToolingベースの静的解析 ツール)が、C/C++ソースを走査してモンゴメリ乗算のパターンを検出する しくみ。

4つの検出基準

1

多倍長走査ループ

語数ぶんを回すforループが2段以上ネストしていること。

2

還元定数による乗算

モンゴメリ定数(n′)を使った語ごとの乗算、または既知の還元関数呼び出し。

mprime · m0inv · n0inv · nprime · qinv · minv · inv · u  |  montgomery_reduce · redc · fpmul_mont · rdc_mont

3

法(モジュラス)の参照

引数または大域定数として法が実際に使われていること。

mod · modulus · N · p · prime · M · m

4

条件付き最終減算(任意)

定数時間化のための末尾補正。判定を後押しする追加シグナル。

検出コマンドとトレース出力

$ montgomery_auto_rewriter --dry-run --trace

// src_converted/mont_word.c を解析

[mont-auto] Function 'mont_word_compute_mprime':
  forDepth=1, redcMul=2, modUse=0, kind=Unknown => SKIP
  reason: need >=2 nested for loops (got 1)
  reason: modulus parameter not referenced

[mont-auto] Function 'montMult_words':

前処理用のmont_word_compute_mprime(Newton法による 逆元計算)はループ深さ1・法未参照のため正しく除外され、 乗算本体のmontMult_wordsだけが検出対象になった。 nwords=-は、SIKEのfpmul_montと 同じく可変長引数を持たない固定長配列設計だったため、 語数パラメータの解決が不要だったことを示す。

2

変換後アーキテクチャ

出典コードのビット単位アルゴリズムは検出対象の構造と一致しないため、 実際には2段階の変換を経ている。

Stage 0 · 出典そのまま

ビット単位 shift-and-add

for(i=mBits;i>0;i--) でX を1ビットずつ処理。 R=2mBits。検出パターン不一致。

→

Stage 1 · 手動再実装(変換前)

語単位 CIOS

montMult_words。32bit×16語、R=2512。 fpmul_montと同型の固定長シグネチャで検出可能に。

→

Stage 2 · 自動変換(変換後)

最適化コアへ委譲

mont::MontOps<>::mul(...) 呼び出しへ本体を 置換。FIOS-CSA-True / Flat の2系統を検証。

Stage 1 → Stage 2: 自動書き換えの中身

変換前 (抜粋)

void montMult_words(
    const uint32_t x[16], y[16],
    const uint32_t m[16],
    uint32_t mprime,
    uint32_t out[16])
{
  // t += x[i]*y (行ごと)
  // t += (t[0]*mprime)*m
  // t >>= 1 word
  // ...16行を素朴なCIOSで実装
}

変換後 (自動生成)

void montMult_words(...)
{
#pragma HLS INLINE off
  // Auto-converted by
  // montgomery_auto_rewriter
  constexpr unsigned MAX_NWORDS = 16;
  mont::MontOps<Digit, MAX_NWORDS>
      ::mul(x, y, out, m,
            mprime, MAX_NWORDS);
}

2つの最適化コア

mont::MontOps<>は既定でFIOS-CSA-True(真の キャリーセーブ表現)へ委譲する。LUT削減を狙う場合は、SIKE研究で 確立した手法と同様に、ディスパッチャを経由せず mont_fios_csa_flat::MontOps_FIOS_CSA_Flat<>::mul(...) を直接呼び出す1行差し替えでFlat版に切り替える。

FIOS-CSA-True

和・桁上げを冗長表現(S, C)のまま全反復にわたって保持し、 最後に1回だけ3:2圧縮器で正規化する。単発レイテンシは最速だが、 圧縮器がLUTベースのためLUT消費が大きい。

FIOS-CSA-Flat

外側ループを完全展開し、通常の+演算子で FPGA内蔵の高速キャリーチェーン(CARRY8)へ直接マッピングする。 速度はTrueにほぼ並びつつLUTを大幅に抑える。

レイテンシ決定化: 最初から組み込んだ3つの選択パターン

「実行時データでループ本体の計算量が変わる」箇所は、HLSの合成 レイテンシが不定(min≠max)になる。今回は3箇所すべてに 「常に計算し、採用するかどうかをビットマスクで選ぶ」定数時間 パターンを設計段階から適用した。

  1. 最終条件付き減算 — t>=mなら t-=mを、分岐ではなく減算後の値との マスク選択に。
  2. 大小比較ループ — 早期breakを 廃し、全16語を常にスキャンしてから結果を確定。
  3. modExpの指数ビット分岐 — 毎回モンゴメリ乗算を 実行し、指数ビットが1かどうかで採用可否だけを選ぶ。

4

リソース削減 — 呼び出し箇所の統合

FIOS-CSA-Flat版をさらに調べたところ、montMult_words がソースコード上の呼び出し箇所ごとに物理的に複製されていることが判明した。 その解消に取り組んだ記録。

発見: 使用時間0.33%の呼び出しがLUTの73%を占めていた

rsa_modexp_hwはmontMult_wordsを 5箇所(ループ外3箇所: MontForm(1) / MontForm(c) / FromMont、 ループ内2箇所: 二乗 / z候補算出)から呼ぶ。合成結果を調べると、 ループ内の2箇所は自動的に1インスタンスへ共有されていた一方、 ループ外の3箇所はそれぞれ専用の物理ハードウェア (1個あたり約87,000〜94,000 LUT)として複製されていた。

複製発覚時のインスタンス内訳(FIOS-CSA-Flat)
呼び出し箇所使用サイクル数LUT割合
ループ内(共有済み・1個) 56,835 95,504 全体の99.7%の時間
MontForm(1) 55 87,182 0.10%の時間
MontForm(c) 73 93,824 0.13%の時間
FromMont 60 87,243 0.11%の時間

ループ外3箇所の合計188サイクル(全体の0.33%)のために、約268,000 LUT(設計全体の73%)が専有されていた。

対策1(失敗): set_directive_allocation

SIKE研究での前例(fp2mul_montの16重複製問題) と同じ手法をまず試したが、今回も真の共有には至らなかった。 呼び出し階層がシンプル(rsa_modexp_hwが 直接5箇所から呼ぶのみ)なため"call is removed"警告こそ出なかった ものの、複製は3インスタンスのまま解消せず、LUTはむしろ微増 するという分かりにくい副作用のみが残った。

対策2(成功): 呼び出し文を1つに統一し、小さなループで反復する

実測から読み取れたVitis HLSの実際の挙動: 同一のループ本体 内で繰り返し実行される、ソース上1つの呼び出し文は自動的に 1インスタンスへ共有される。一方、別々の文として書かれた 呼び出しは、たとえ同じ関数への呼び出しであっても複製 される。この性質を利用し、ループ外の呼び出しを人為的に小さな ループへ統一した。

Before — 複製される

montMult_words(
    one, r2m, m, mprime,
    zarr1);
montMult_words(
    c, r2m, m, mprime,
    parr1);

After — 共有される

uint32_t x[2][N], y[2][N],
         out[2][N];
x[0]=one; y[0]=r2m;
x[1]=c;   y[1]=r2m;
for (unsigned s=0; s<2; s++)
  montMult_words(
      x[s], y[s], m,
      mprime, out[s]);

副作用: 部分適用は既存の共有を壊す

この書き換えをループ外の2箇所だけに適用したところ、狙い通り そこは1インスタンスへ統合された。しかし副作用として、 元々共有できていたループ内の2箇所(二乗/z候補)の共有が崩れ、 2インスタンスに分裂してしまった。Vitisの資源バインディング は関数全体を通した大域的な判断をしているらしく、一部だけの 修正では予測できない影響が出る。関数内の全ての同種呼び出し 箇所に一貫してこのパターンを適用することで解決した。

呼び出し統合の前後比較(FIOS-CSA-Flat)
構成物理

統合前 4 367,870 (21%) 429 (3%) 85% 57,051 cyc
統合後 3 283,587 (16%) 363 (3%) 65% 56,585 cyc

要点

LUTを22.9%削減(367,870 → 283,587)、DSPを15.4%削減 (429 → 363)しながら、レイテンシも0.8%改善(57,051 → 56,585 サイクル) — 速度を犠牲にせずリソースを削減できた。 残るFromMont(復号の最後に1回だけ呼ばれる、 86,870 LUT)はペアになる呼び出しが存在しないため統合不可能で、 既知の残存コストとして受け入れている。

5

速度重視オプションの確立

リソース重視版を基準に3つの追加改善案を検証し、最終的に 速度重視オプションとして確立した記録。

検証した3案

A

FromMontを追加でループへ包む

効果なし(LUT 284,201 ≈ 283,587)。ペアになる呼び出しが 存在しない孤立した呼び出しは、ループで包むだけでは共有先が 生まれない。

B

4bit固定窓法(windowed exponentiation)

乗算回数を約1027回→約657回に削減するアルゴリズム 改善。実装に落とし穴があった(下記参照)。

C

ループ内二乗/z候補の並列化

18.1%高速化(46,336 cyc)したが、LUTが32.9%増加 (376,955)。明確な速度対リソースのトレードオフ。

落とし穴: UNROLL付け忘れによる大幅な性能劣化

案Bの定数時間テーブル参照(16エントリ×16語=256回のAND/OR 選択)に#pragma HLS UNROLLを付け忘れたところ、 窓1つあたり602サイクルという直列オーバーヘッドが生じ、 理論上は高速化するはずが実際には38%悪化した(78,099 cycle)。UNROLL追加で45,460 cycle(19.7%高速化)まで 改善したが、今度はテーブル構築部分(事前変換+事前計算チェーン) が別ループ形状のため複製され、LUTが40.2%増加した。 アルゴリズム的な演算回数削減だけでは不十分で、各ループの 並列化指定を個別に確認する必要がある。

窓法 + 呼び出し統合 → 実用的な速度重視オプション

案Bに、Section 4で確立した「呼び出し箇所を1つのループへ統合する」 手法を適用した。事前変換2回と事前計算チェーン14回を、 j=0..15の1つのループへ統合する (jはループ変数であり実行時の秘密データ ではないため、if(j==0) else if(j==1) のような分岐は定数時間性を損なわない)。これにより物理インスタンス 数が4→3へ削減された。

最終2オプションの比較
構成サイクル数実時間LUTDSP
リソース重視(Section 4) 56,585 0.566 ms 283,587 (16% / SLR65%) 363
速度重視(窓法+統合) 46,044 0.460 ms 305,063 (18% / SLR70%) 359

要点

速度重視オプションは、リソース重視版に対しDSPをむしろわずかに 減らし(363 → 359)、LUT増加をわずか7.6%に抑えながら 18.6%高速化した(56,585 → 46,044 cycle)。窓法単体 (統合前、LUT+40.2%)から呼び出し統合によって大幅に改善した形。

6

リソース最小化オプション

「性能は控えめにして、さらにリソースを削減したい」という方向の 第3のオプション。呼び出し構造はそのままに、乗算器コア自体を より軽量なものへ差し替えた。

FIOS-CSA-Flat(空間並列) vs MontOps_Fast(時分割再利用)

FIOS-CSA-Flatは、CIOSの外側16反復ループを #pragma HLS UNROLLで完全展開し、16個の 乗算器群を空間的に並べて配置する。一方 montgomery_converter/include/mont_ops_fast.hpp のMontOps_Fast<T,NWORDS>は、外側 ループを#pragma HLS PIPELINEにとどめ、 同じ乗算器群を16反復にわたって時分割で再利用する 古典的CIOS実装。シグネチャが完全に同一 (mul(a,b,c,mod,mprime))なため、 mont_word.cppのinclude文と呼び出し1行を 差し替えるだけで、これまでの呼び出し統合の仕組みをそのまま 流用できた。

3オプションの全体比較
構成サイクル数実時間LUTDSP
速度重視(窓法+統合) 46,044 0.460 ms 305,063 (18%) 359
バランス(FIOS-CSA-Flat+統合) 56,585 0.566 ms 283,587 (16%) 363
リソース最小(MontOps_Fast) 126,311 1.263 ms 17,983 (1%) 110

要点

リソース最小オプションはLUTを93.7%削減(283,587 → 17,983)、 DSPを69.7%削減(363 → 110)する代わりに、レイテンシが 2.23倍(56,585 → 126,311 cycle)になる。驚くべきことに、 この構成は変換前(素のCIOS、27,526 LUT)よりもさらに 小さいLUT使用量になった。「変換」という行為自体が 必ずしもリソース増加を意味するわけではなく、どのコアを選ぶか 次第で、変換前を下回るフットプリントで、なおかつ検出・自動 変換パイプラインの恩恵(コア差し替えの容易さ)を享受できる ことを示す実例となった。

3つのオプション

RSA_Montgomery_HLS/には現在3つの 実用的なオプションが揃っている: 速度重視(src_converted_flat_speed/)、 バランス(src_converted_flat/)、 リソース最小(src_converted_lean/)。 いずれも同じ検出・変換パイプラインと呼び出し統合の仕組みを共有し、 乗算器コアとアルゴリズム構造だけを用途に応じて選択できる。
